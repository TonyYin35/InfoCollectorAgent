一、产品名称与定位
名称（暂定）：Info Radar（信息雷达）
定位：面向“同城活动发现”的检索+汇总+提炼助手。用户打开网页后，系统基于定位/城市与默认筛选条件，自动检索多来源活动信息，输出结构化活动卡片列表，并允许用户通过对话修改条件与追问细节。
核心原则：可追溯（每条都有来源证据）、可去重（同一活动多来源聚合）、可筛选（时间/距离/类型）。

二、目标用户与典型场景
目标用户：对同城“漫展/快闪/同好活动/外拍集合”等活动有强发现需求的人。
典型场景：
1）用户打开网页，想快速知道“我附近未来一周有哪些漫展/快闪”。
2）用户看到列表后想进一步限制条件（只看周末、只看免费、只看滨江区附近）。
3）用户想问某个活动的细节（地点怎么去、是否需要预约、活动时间是否确定、是否有票务链接）。

三、MVP 范围与非目标
MVP 必做范围：

首屏自动生成活动列表（默认 Top 10）。

支持定位或手动选择城市（定位拒绝/失败必须可用）。

活动卡片结构化字段输出 + 来源链接 + 证据摘录。

去重聚合（同一活动跨来源合并）。

基础筛选：时间窗、距离/同城、活动类型。

对话框：允许用户用自然语言修改筛选条件并触发重新检索；允许对单条活动追问（基于已抓取证据回答）。

MVP 明确不做：

不承诺“全网覆盖/百分百及时”。

不做登录体系、关注体系、个性化长期画像。

不做推送订阅（邮件/微信/通知）——先做按需访问。

不做“真伪裁决”；只做多源一致性/冲突提示与证据回链。

四、核心用户流程（User Flow）
1）用户访问网站首页。
2）系统请求定位权限：

允许：获取经纬度（或只获取城市级别），进入流程 3。

拒绝/失败：展示城市选择组件（默认可选“上次城市/热门城市/手动输入”），用户选定后进入流程 3。
3）系统按默认条件执行检索：

默认条件（可配置）：

时间窗：未来 7 天（含今天）

距离：同城（MVP 可先不做精确公里，使用城市级别；若有坐标则可附加“附近优先”排序）

类型：漫展/快闪/同好活动（MVP 先做三类）

数量：10 条
4）前端展示 Top 10 活动卡片流，并提供筛选控件：时间窗、类型、（可选）距离。
5）用户可在对话框输入自然语言：

修改条件（例如“只看周末”“我在滨江区”“只要免费活动”）→ 触发后端重新检索并刷新列表。

追问活动细节（例如“第2个活动怎么报名？”）→ 后端基于该活动证据片段作答，并附来源链接；若证据不足则明确说明“页面未提供/未抓到”。

五、活动数据结构（MVP 最小字段）
后端输出统一 Event（事件）对象，至少包含：

event_id：内部 ID（聚类后生成）

title：活动名称（字符串）

time_text：时间描述原文（字符串，可空）

start_time / end_time：标准化时间（ISO，可空；若不确定则留空并保留 time_text）

location_text：地点/场馆/地址线索（字符串，可空）

city：城市（必填，用于筛选）

category：枚举（cosplay_convention / pop_up / meetup_or_photowalk / other）

participation_info：参与方式线索（购票/报名/集合/预约关键词摘要，可空）

source_urls：来源列表（至少 1 个 URL；聚类后可能多个）

primary_source_url：主来源 URL（用于点击跳转）

evidence_snippets：证据摘录列表（每条≤200字，含摘录文本+对应 URL）

fetched_at：抓取时间（ISO）

published_at：页面发布时间（可选，有则填）

confidence：置信度（low/medium/high，基于字段完整度与来源类型的规则评分）

六、信息来源策略（MVP 约束）
MVP 数据源不要求覆盖微博/小红书/B站的深层内容；优先选择：
1）通用搜索引擎召回（召回层）：用 query 在公开网页中找候选 URL。
2）活动/票务聚合站与场馆活动页（结构相对稳定、公开可访问）作为主要高可信来源。
3）后续扩展再做平台 Adapter（微博/B站/小红书）与反爬处理。

必须遵守：

每条输出必须带 URL 回链与抓取时间。

若某来源抓取失败，系统必须降级到其他来源，并在 debug 字段记录失败原因（前端可不展示）。

七、排序与去重（MVP 规则版）
去重聚类规则（简化）：

URL 完全相同：同条。

title 相似度高（阈值可配）且时间线索接近且地点线索相近：合并为同一 event。

合并后保留多个 source_urls，并选可信度更高/字段更完整的为 primary_source_url。

排序规则（可解释、规则版）：
综合得分 = 时间匹配 + 地点匹配 + 来源可信度 + 内容完整度

时间匹配：发生时间越近（且在时间窗内）分越高；只出现“近期/本周”但无具体时间则中等分。

地点匹配：命中用户城市/区域关键词加分。

来源可信度：票务/场馆官网 > 聚合站 > 个人转述/搬运页。

内容完整度：含明确时间+地点+参与方式线索的加分。

八、对话能力（MVP 约束）
对话框支持两类指令：
1）条件变更类（触发重新检索）：

时间：今天/本周/周末/未来7天/未来30天

地点：城市名/区名/地标关键词（MVP 先做字符串匹配）

类型：漫展/快闪/外拍/同好会（映射到 category）

数量：给我 5 条/10 条/20 条
2）详情追问类（不重新检索，基于证据回答）：

“怎么报名/哪里买票/几点开始/地点在哪/有没有费用”
要求：回答必须引用已抓取的 evidence_snippets 或明确说明证据不足，并附 primary_source_url。

九、前端需求（MVP）
页面结构：

首页：

顶部：城市显示（定位城市或手动选择）、刷新按钮

筛选条：时间窗、类型（多选/单选）、（可选）距离/同城

主体：活动卡片列表（Top 10）

侧边/底部：对话框（输入框+历史消息）

活动卡片展示字段：

标题

时间（若无则显示“时间未明确”）

地点（若无则显示“地点线索不足”）

参与方式线索（若无则不显示）

来源按钮（跳转 primary_source_url）

“证据”展开（展示 evidence_snippet）

交互要求：

首屏加载要有骨架屏/加载提示。

检索失败要有可行动提示：例如“无法获取定位，已切换到城市选择”。

每次检索应显示“更新时间/抓取时间”。

十、后端 API（MVP 建议）
1）POST /api/search
请求：

location: { lat?, lng?, city? }

filters: { time_window_days, categories[], keyword?, limit }
响应：

events: Event[]（结构见上）

meta: { query_plan_summary, sources_used, fetched_at, warnings[] }

2）POST /api/chat
请求：

session_id

user_message

current_state: { location, filters, last_events[] ids }
响应：

assistant_message（文本）

action: { type: "refetch"|"answer_only", updated_filters?, focus_event_id? }

events?（若 refetch，返回新的 events 列表）

十一、日志与可观测性（MVP 必须但可不展示给用户）

每次检索保存：QuerySpec、sources_used、候选 URL 数、成功抓取数、失败原因统计、去重前后数量。

每个 event 保存：聚类来源列表、选主来源理由（规则信号）、字段抽取置信度。

十二、验收标准（MVP 可测试、可量化）
功能验收：
1）在定位允许与拒绝两种情况下都能得到活动列表（非空或合理提示）。
2）返回 Top 10，每条都有 primary_source_url + fetched_at + 至少 1 条 evidence_snippet。
3）重复率：Top 10 中同一活动不超过 2 条（通过聚类验证）。
4）相关性：在“杭州 + 未来7天 + 漫展/快闪”条件下，列表中明显无关内容占比可控（例如 ≤20%）。
5）对话改条件能触发刷新，且筛选确实生效（例如“只看周末”后工作日活动明显减少）。
6）详情追问不会编造：证据不足时明确说明并附链接。

十三、风险与降级策略（MVP 必须写清）

定位失败：城市选择降级。

搜索 provider 失败：切换备用 provider 或返回“候选不足”并提示刷新/更换时间窗。

抓取失败/反爬：跳过该 URL，记录 warnings，确保仍返回其他来源结果。

时间地点抽取失败：字段留空，但必须保留原文片段与链接，避免伪精确。

这份需求可以直接交给工程开始拆任务：前端页面、后端 API、检索流水线、字段抽取、去重排序、对话路由。你后续如果要继续细化，我建议下一步只做两件事：
1）把“活动类型枚举与关键词映射表”定稿（决定 extractor 与分类）；
2）把“首批数据源清单（3~5 个站点/入口）”定稿（决定 MVP 是否稳定可跑）。
